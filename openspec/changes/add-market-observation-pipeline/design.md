## Context

Мотивация — в `proposal.md` §Why. Требования — в `specs/`. Здесь только то, что нужно,
чтобы объяснить подход.

Четыре внешних факта формируют всю конструкцию:

1. **Атомарного среза региона ESI не даёт.** Стакан пагинируется, крупный регион — это
   двести с лишним страниц, собираемых десятки секунд, в течение которых данные меняются.
2. **Правка ордера имеет точное время, а исполнение наблюдаемо.** `issued` — таймштамп
   последней правки, а не дата создания; правка сбрасывает длительность ордера
   (дев-блог CCP «Broker Relations»). Уменьшение остатка при неподвижном `issued` —
   сделка по этому ордеру. Неоднозначно только полное исчезновение: выкуп, отмена и
   истечение неотличимы, хотя истечение вычислимо из `issued` и длительности.
3. **Игра ограничивает правку ордера пятью минутами**, и ESI кэширует стакан те же пять
   минут. Наблюдение с шагом пять минут по границе срока годности — это частота Найквиста
   для процесса перестановок: полнее не бывает, реже — теряется.
4. **История покупается, свежая полнота — нет.** Дневная история публикуется с 2003 года,
   ордербук по всем регионам — с 2017 года с шагом 30 минут. Тридцать минут
   недосэмплируют перестановки в шесть раз, и это невосполнимо.

Плюс два принятых решения проекта: счётная логика в C# (хранилище отдаёт плоские
строки — отлаживается пошагово), стиль архитектуры **layered**
(`.agents/rules/csharp/local-project-layers.md`).

## Goals / Non-Goals

**Goals:**

- Начать бэктест на архиве немедленно, не дожидаясь накопления.
- Собирать живьём то, что архив не даёт: полный поток перестановок с точными временами.
- Держать локально столько, сколько нужно вопросу, а не сколько существует.
- Уложить свёртку миллиона ордеров в бюджет наблюдения без пауз GC.
- Оставить сырьё пригодным для признаков, которые ещё не придуманы.

**Non-Goals:**

- Оптимизация под объёмы, которых не будет. Одна машина, один процесс.
- Низкая задержка. Данные обновляются раз в пять минут по решению CCP.
- Полная локальная копия архива. Девять лет ордербука локально не нужны — см. решение об
  окне.

## Decisions

### Два источника, одна схема

```
┌──────────────┐   ┌──────────────────┐   ┌──────────────┐
│ живой ESI    │   │ архив снимков    │   │ реплей       │
│ хабы, 5 мин  │   │ интервалами      │   │ своего озера │
└──────┬───────┘   └────────┬─────────┘   └──────┬───────┘
       └────────────────────┴────────────────────┘
                            ▼
              одна свёртка, одна схема фактов
```

Источник объявляет свой шаг наблюдения, и шаг переносится в записи покрытия. Это
единственное, чем потребитель имеет право различать происхождение факта: события
перестановки, полученные с шагом 30 минут, помечены неполными, потому что игра допускает
до шести правок за этот интервал.

### Окно локального хранения: 24 месяца ордербука

Довод не размер, а **нестационарность.** Патчи CCP меняли экономику скачком: правки
чертежей, дропов, новых типов. Микроструктура 2017 года не предсказывает 2026-й, и
обучение на данных через границу патча учится на двух разных мирах. Окно — настройка, не
константа; интервалы вне окна остаются доступны наверху.

Дневная история под окно не подпадает: 4.4 ГиБ за двадцать три года — это плата, которую
нет смысла экономить, а тренды и сезонность живут именно там.

### Единица загрузки — интервал времени, не регион

Архивные снимки публикуются как глобальные срезы на момент: один файл — все регионы за
один таймштамп. Выбрать регион при скачивании нельзя.

Отсюда неочевидное следствие: **отбрасывать нехабовые регионы из уже скачанного файла
бессмысленно.** Трафик оплачен, а хранение событий по тихому региону почти ничего не
стоит — там мало что меняется. Поэтому за материализованный интервал берутся все регионы,
а «опциональность» живёт в выборе интервала и в том, что живой сбор идёт по хабам.

| | загрузка | хранение |
|---|---|---|
| дневная история, все регионы, 2003→ | ~4.4 ГиБ | ~1–2 ГиБ в Parquet |
| ордербук, окно 24 месяца, все регионы | ~700 ГиБ | ~60–120 ГиБ в событиях |
| живой сбор, хабы, 5 мин | ~1–2 ГиБ/сутки | ~0.1–0.3 ГиБ/сутки |
| ордербук 2017→2024 | по требованию | не материализуется |

Все числа — предмет замера. Порядок конвертации важен: архив приходит в CSV под bz2/gz,
Parquet у источников нет, поэтому окно один раз протаскивается через тот же конвейер
свёртки, что и живые наблюдения.

### Одна проходка вместо двух

Дифф с предыдущим наблюдением, разметка вида события и вычисление признаков — **один
проход по стакану в памяти**, не два и не запрос к хранилищу.

Полный стакан региона всё равно должен быть в памяти: дифф без него невозможен. Пока мы
по нему идём, разметка и признаки получаются попутно.

Альтернатива — считать признаки запросом после записи событий — отвергнута: каждый такой
запрос тянет через процесс миллионы строк на каждом наблюдении.

### Разметка вида события

```
                    ┌─ issued изменился ─┬─ цена изменилась ──▶ перестановка цены
                    │                    │                      (время события = issued)
ордер есть в обоих ─┤                    └─ цена та же ────────▶ пополнение склада NPC
    наблюдениях     │                                            (если отпечаток NPC)
                    └─ issued тот же ────── остаток меньше ────▶ наблюдённое исполнение
                                                                  (время = интервал)
```

**Отпечаток NPC обязателен, а не желателен.** Ордера NPC узнаются по совокупности:
идентификатор ниже порога, длительность 365 суток, остаток равен полному объёму, круглая
цена, сторона продажи. При пополнении склада им переставляют `issued` без изменения цены;
без фильтра каждое пополнение попадёт в обучение как действие конкурента, причём именно
по тем предметам, которыми торгуют новички.

**Появление даёт момент создания только при пятиминутном шаге.** Новый ордер не может
быть отредактирован в первые пять минут жизни, поэтому при шаге пять минут `issued` у
впервые увиденного идентификатора — это момент создания. При тридцатиминутном шаге такой
гарантии нет, и `issued` остаётся моментом последней правки.

### Исчезновение подтверждается окном

Источник допускает пропуски: ордер исчезает из одного снимка и возвращается в следующем,
хотя идентификаторы уникальны и не переиспользуются. Исчезновение по единственному
сравнению — систематическая выдумка на дефектах источника, и выдумка эта выглядит именно
как исполнение.

Поэтому исчезновение — состояние процесса до подтверждения и факт после. Время события
указывает интервал между последним наблюдением ордера и первым отсутствием, время
наблюдения — момент подтверждения. Пропуски учитываются в покрытии: их частота и есть
основание для выбора длины окна.

### Формат представления в горячем пути

Миллион записей каждые пять минут не допускает объектной модели.

| | решение | почему не иначе |
|---|---|---|
| представление ордера | `struct` фиксированного размера в массиве | миллион объектов на наблюдение — GC-паузы вместо работы |
| буферы | два поколения массивов на регион, переиспользуются | новый массив на наблюдение фрагментирует LOH |
| индекс по идентификатору | открытая адресация поверх массива | `Dictionary` на миллион записей — десятки МБ накладных и худшая локальность |
| разбор ответа | потоковый разбор через `Utf8JsonReader` прямо в массив | `JsonSerializer` в коллекцию — тот же миллион объектов |
| цена | целое в сотых долях ISK | `double` теряет точность на сравнении цен, `decimal` слишком дорог в цикле |

Оценка памяти: миллион ордеров при ~64 байтах — 64 МБ на поколение, два поколения плюс
индекс — порядка 200 МБ на полный охват. Это единственное место, где код пишется
«неудобно, зато без аллокаций».

### Хранилище: Parquet-озеро, DuckDB как движок запросов

Пакеты: `Parquet.Net` для записи, `DuckDB.NET.Data.Full` для чтения.

Решающий довод — **отсутствие второго кода, трогающего данные.** Обучение будет читать те
же файлы напрямую, без экспорта. Экспорт означал бы вторую реализацию доступа к данным, а
значит расхождение обучения и боя — дефект, который на бэктесте выглядит как отличная
модель, а в бою как случайная.

ClickHouse — правильный ответ на вопрос, которого у нас нет: он нужен, когда объём
перестаёт влезать в одну машину. Цена его выбора сейчас — обязательный экспорт для
обучения, то есть ровно та щель, которую мы закрываем.

**Граница SQL и C# проходит по потребителю, а не по сложности.** Всё, что попадает в
признак, сигнал или обучающую выборку, считается только в C#; хранилище в этих запросах
делает лишь отбор, проекцию и отсечение партиций. Агрегация средствами DuckDB разрешена
исключительно для отчётов оператору — покрытие, расход трафика, диагностика, — где
расхождение обучения с боем не существует по определению. Технически разведено двумя
разными портами в application, чтобы посчитать признак через SQL было нельзя случайно.

Ограничение принято сознательно: **один процесс-писатель.** Компакция выполняется вне
пиков.

### Раскладка озера

```
facts/
  order-events/       observed_date=YYYY-MM-DD/region=<id>/*.parquet
  order-baselines/    observed_date=.../region=<id>/*.parquet
  book-checkpoints/   observed_date=.../region=<id>/*.parquet
  book-features/      observed_date=.../region=<id>/*.parquet
  history-daily/      as_of_date=YYYY-MM-DD/region=<id>/*.parquet
  coverage/           observed_date=.../*.parquet
materialization/      реестр интервалов
raw-pages/            скользящее окно 48 часов, только для разбора дефектов парсера
```

Партиционирование по дате наблюдения и региону: запрос за интервал отсекает лишнее по
путям, суточная партиция — естественная единица компакции. Внутри файла сортировка по
«тип, локация, сторона, цена» — признаки и восстановление читают непрерывные диапазоны.

Дневная история партиционируется **по времени получения**, а не по календарной дате
строки: строка за сегодня переполучается в течение суток, и версии обязаны лежать
раздельно.

### Суточные чекпойнты

Без чекпойнтов восстановление состояния на момент сворачивает всю историю региона — через
год это миллиарды строк на один запрос, то есть требование записано, а исполнить его
нельзя.

Суточный чекпойнт полного стакана региона стоит около миллиона строк в сутки на полный
охват, порядка 10–15 МБ сжатого — на фоне событий шум. Часовой чекпойнт даёт в двадцать
четыре раза больше и не нужен: бэктест не спрашивает точку, он проходит интервал подряд.

### Идемпотентность и определение факта

Наблюдение пишется во временный файл и вводится в озеро атомарным переименованием;
запись покрытия добавляется последней.

Отсюда определение, снимающее противоречие между идемпотентностью и неизменяемостью:
**факт — это строка, подтверждённая записью покрытия.** Неподтверждённый файл фактом ещё
не стал, читателям не виден и подлежит уборке. Неизменяемость применяется к фактам,
уборка — к неподтверждённым файлам. Источник истины о том, что наблюдение состоялось, —
журнал покрытия, а не файловая система.

### Планировщик: один воркер-диспетчер

`csharp/background-workers.md` требует, чтобы периодические воркеры наследовали проектный
`ScheduledWorkerBase`, и первый воркер эту базу и заводит: `AdaptivePollSchedule`,
DI-scope на цикл, счётчики через `[Counter]`.

Форма — **один диспетчер**, который каждый цикл берёт регионы с истёкшим сроком
наблюдения. Альтернатива «воркер на регион» даёт изоляцию отказов, но превращает общий
бюджет ошибок в разделяемое состояние между шестьюдесятью восемью воркерами, а «один
писатель» — в очередь. История и компакция — отдельные воркеры: правило запрещает
склеивать разные задачи в один воркер.

Общего среза мира не существует — у регионов разный темп, и срок годности источника
смещается на секунды, поэтому расписание ведётся по заголовкам ответа, а не по сетке.
Следствие в схеме: события и признаки ключуются `(регион, время наблюдения)`; глобального
номера наблюдения нет и быть не может.

### Реплей — источник, а не режим

Приём объявляет порт «источник наблюдений»; его реализуют живой ESI, импорт архива и
чтение собственного озера. Время наблюдения приходит вместе с наблюдением, домен получает
его аргументом.

Вход реплея собственных данных — **восстановленные наблюдения** (чекпойнт плюс события), а
не сырые страницы: хранить страницы вечно означало бы терабайты в год ради данных, которые
полностью выводимы. Скользящее окно сырых страниц на 48 часов существует только для
разбора дефектов парсера и источником истины не является.

Запрет «сейчас» в домене проверяется анализатором:
`Microsoft.CodeAnalysis.BannedApiAnalyzers` банит `DateTime.UtcNow`, `DateTimeOffset.Now`
и `TimeProvider.System` в доменном проекте. NetArchTest для этого не годится — он смотрит
на зависимости типов, а не на вызовы; законы слоёв остаются за ним.

### Отклонение от раскладки правил

`csharp/architecture.md` описывает layered как `presentation → application → domain ←
infrastructure`. `csharp/project-naming-and-setup.md` §1–4 и
`csharp/project-deps-and-tests.md` §1 описывают раскладку layered-проекта как
`application/ feature/ database/ client/ models/ shared/ generation/ bots/`. Оба правила
`always: true` и расходятся между собой.

Берём первую: вторая сервисной формы — `database/` подразумевает `DbContext`, которого
здесь нет, `models/` описан как «типы, пересекающие границы проектов», а не «вся счётная
логика». Натянуть на неё жирный домен можно только соврав в названиях. Отклонение
зафиксировано в `local-project-layers.md`, конфликт поднимается наверх в `nova/meta/rules`
отдельной задачей — правило про layered должно быть согласовано само с собой.

Тестовый стек — фиксированный набор из `csharp/testing-stack-and-pyramid.md`
(xUnit v3, Shouldly, NSubstitute, NetArchTest.Rules, Coverlet).

## Risks / Trade-offs

- **Отпечаток NPC может оказаться неполным** → выборка перестановок будет содержать
  пополнения складов, и модель поведения конкурентов обучится на движениях NPC. Проверка
  дешёвая и обязательная: на архиве видно, остаются ли после фильтра ордера с двинувшимся
  `issued` и неизменной ценой.
- **Длина окна подтверждения исчезновения не известна** → слишком короткое даёт ложные
  исчезновения, слишком длинное задерживает факт. Измеряется по архиву: частота пропусков
  источника видна за годы.
- **Доля изменившихся ордеров за наблюдение неизвестна** (оценка 5–15 %, от неё линейно
  зависит объём) → метрика выносится в наблюдаемость. Если доля втрое выше ожидаемой,
  бюджет пересматривается, а не подгоняется удалением сырья.
- **Порванный срез неустраним** → не устраняем, а перестаём претендовать: время
  фиксируется на страницу, наблюдение несёт границы интервала. Для перестановок это
  лечится `issued`, для исполнений остаётся интервалом.
- **Один писатель в озеро** → компакция и запись конкурируют за диск; суточные партиции
  делают компакцию порционной.
- **Производительность записи Parquet из .NET не измерена** → замер на первом регионе;
  вариант отхода — писать сырые батчи и сворачивать их отдельной стадией.
- **Конвертация окна архива — разовая работа на сотни ГиБ** → протаскивается тем же
  конвейером, что живой сбор, порциями по суткам, с возможностью продолжить с места
  обрыва.
- **Лицензия архива не открытая** → массовое скачивание разрешено автором прямым текстом,
  вежливость — два потока и уважение метаданных о времени изменения. Данные производны от
  ESI и подпадают под CCP Developer License. Для личного проекта приемлемо; публикация
  продукта потребует отдельного разбора.
- **Сырьё в пределах окна хранится бессрочно** → сознательный обмен диска на возможность
  переобучить модель с признаком, которого сегодня нет.

## Migration Plan

Миграции нет — репозиторий пустой, внешних потребителей нет. Порядок ввода выбран так,
чтобы обучающие данные появились на первой неделе:

1. Скелет решения, гейты, `ScheduledWorkerBase`.
2. Озеро, покрытие, реестр материализации, идемпотентная запись.
3. Импорт дневной истории целиком — первый пригодный для обучения набор.
4. Свёртка: разметка событий и признаки в одной проходке.
5. Импорт окна ордербука из архива — бэктест микроструктуры становится возможен.
6. Клиент ESI с бюджетом ошибок и условными запросами; живой сбор по хабам на 5 минутах.
7. Реплей и сверка: реплей даёт тот же результат, что живой прогон.
8. Расширение живого охвата за пределы хабов — по результатам замеров.

Откат на любом шаге — удаление озера и перезапуск; внешнего состояния система не меняет,
в игру ничего не пишет.

## Open Questions

Все проверяются замером и ни один не меняет спеки, подход или разбивку задач.

- **Пороги глубины стакана.** Какие отклонения от лучшей цены считать (1 %, 5 %, ещё?).
  Набор порогов — параметр вычисления признаков; менять дёшево, пока признаки
  перестраиваются из сырья.
- **Точная длина окна подтверждения исчезновения.** Стартовое значение — два
  последовательных полных наблюдения; уточняется по частоте пропусков в архиве.
- **Полнота отпечатка NPC.** Порог идентификатора и совокупность признаков подтверждаются
  на архиве.
- **Рынки игровых структур.** По описанию источника архивные снимки региональных ордеров
  включают публично доступные структуры, то есть пара Jita 4-4 ↔ Перимитер должна быть
  видна. Подтверждается наличием идентификатора локации Перимитера в снимке по The Forge.
- **Фактическое число торгуемых типов.** Считается по дневной истории после её импорта;
  задаёт размер признаковых партиций.
