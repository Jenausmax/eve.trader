## Context

Мотивация — в `proposal.md` §Why. Здесь только то, что определяет форму решения.

Что уже есть и на что решение опирается:

- **Озеро фактов** — Parquet под `facts/<набор>/observed_date=…/region=…/`, запись
  атомарной подменой файла, покрытие пишется последним. Отсюда бесплатное свойство:
  читатель, отбирающий строки по записям покрытия, недописанных партиций не видит —
  `market-facts/bitemporal-store` §«Факт — строка, подтверждённая покрытием».
- **Два порта чтения**, намеренно разных: `IFactRowReader` отдаёт плоские строки и
  обслуживает домен, `IOperationalReportReader` агрегирует и обслуживает отчёты
  оператору. Граница записана нормой `bitemporal-store` §«Границы вычислений в
  хранилище» и в этом изменении не двигается.
- **`CliContext`** — обвязка озера, собираемая на команду: layout, покрытие, реестр,
  оба читателя, телеметрия. API нужна та же обвязка, но на процесс, а не на вызов.
- **Приёмка конвейера пройдена** (`add-pipeline-acceptance`), то есть читать есть что и
  прочитанному можно верить.

Чего нет: HTTP-поверхности любого вида, фронтенда, генерации клиента.

Ограничение сверху: канон владельца в `.agents/rules/typescript/` фиксирует стек
целиком (React 19, Vite, bun, Tailwind 4, Base UI/shadcn, TanStack Query/Router,
i18next) и гейт из трёх команд. Выбирать здесь нечего, кроме графиков — их правила не
покрывают.

## Goals / Non-Goals

**Goals:**

- HTTP-поверхность только для чтения, поднимающаяся и падающая независимо от сбора.
- Контракт, из которого клиент порождается, а не пишется.
- Экраны, на которых пробел выглядит пробелом, а неполное наблюдение — неполным.
- Графики, выдерживающие объём, который даёт конвейер.

**Non-Goals:**

- Пишущие пути, авторизация, многопользовательский режим — см. proposal §Non-goals.
- Кэш поверх озера. Пока не измерена задержка запроса, кэш — преждевременная
  оптимизация, вносящая второй источник истины.
- Стриминг и подписки. Обновление по таймеру TanStack Query достаточно для шага
  наблюдения в минуты; WebSocket-канал добавил бы состояние в процесс, который
  специально сделан без состояния.
- Экраны сигналов и обучения. Приедут своими изменениями.

## Decisions

### Отдельный процесс, а не эндпоинт внутри коллектора

`EveTrader.Api` в `src/presentation/` рядом с `EveTrader.Cli`. Слой тот же —
presentation; домен и application не меняются.

Альтернатива — поднять HTTP внутри процесса сбора — отвергнута по двум причинам.
Первая: сбор обязан переживать перезапуск интерфейса и наоборот, а в одном процессе
падение веб-части уносит наблюдение, восстановить которое нельзя — момент прошёл.
Вторая: у процессов разный профиль — коллектор держит стакан региона в памяти и живёт
часами, API отвечает за миллисекунды и не копит ничего.

Цена решения названа в proposal: вторая точка настройки пути к озеру и вторая точка
наблюдаемости. Обе разрешаются существующими правилами (`config-resolution.md`,
`observability/diagnostics.md`), новых механизмов не требуется.

### Обвязка озера — на процесс, а не на запрос

`CliContext` собирается на команду, потому что команда живёт один прогон. У API иначе:
`LakeLayout`, покрытие, реестр и оба читателя заводятся один раз при старте и живут с
процессом. Соединение DuckDB открывается на запрос — оно дешёвое и потокобезопасным
его считать не за что.

### Minimal API, контракт — источник клиента

`csharp/api-design.md` относится к проектам с контроллерами; для поверхности из полутора
десятков путей только для чтения контроллеры — церемония.

Порядок: описание контракта порождается из кода, клиент TypeScript — из описания.
Рукописный клиент отвергнут: расхождение с контрактом он обнаруживает в бою, а
порождённый — при сборке фронтенда, то есть внутри гейта.

Design-first (сначала руками описание, потом код) отвергнут как третье место, где
живёт форма ответа, при двух уже имеющихся.

### Поверхность делится на две по границе вычисления, а не по экрану

`api/query-surface` отдаёт плоские факты и ничего не агрегирует. `api/operations-surface`
отдаёт отчёты и агрегирует средствами хранилища.

Граница не косметическая: норма разрешает агрегацию в хранилище только для отчётов
оператору. Разделив пути, мы делаем нарушение видимым — агрегат, приехавший по пути
фактов, виден в контракте. Деление по экранам («рынок» и «состояние») такого свойства не
даёт: рыночному экрану тоже нужны отчёты.

### Признаки и обучение мимо HTTP — записано требованием

Соблазн очевиден: поверхность уже отдаёт факты, значит через неё удобно собрать
выборку. Это второе место вычисления; расхождение с боевым путём проявляется как
отличный бэктест и случайный бой. Запрещено требованием
`api/query-surface` §«Поверхность запроса не путь для признаков», а не только словами
здесь.

### Пустота в ответе всегда объяснена

Технически проще вернуть пустой массив. Отвергнуто: три состояния покрытия — центральное
свойство конвейера, и поверхность, теряющая их на границе HTTP, обесценивает журнал
покрытия целиком. Поэтому ответ несёт состояние покрытия интервала всегда, а не только
когда данные есть.

### Ограничение выдачи обязательно и объявлено

Стакан крупного региона — сотни тысяч ордеров, признаки хаба за сутки — сотни тысяч
строк. Интервал в запросе обязателен, ответ ограничен по размеру и несёт признак
продолжения. Запрос без границ отклоняется, а не исполняется: отказ с объяснением
дешевле, чем ответ, кладущий обе стороны.

### Графики — `lightweight-charts`, и почему не остальные

Единственное место, где правила выбора не дают.

- `recharts` — рисует SVG, узел на точку; на рядах в сотни тысяч точек умирает. Не
  используется.
- `lightweight-charts` — canvas, сделана под финансовые ряды, из коробки умеет разрывы
  во времени. Разрыв важнее удобства: норма требует показывать ненаблюдавшийся интервал
  разрывом, а не прямой.
- `uplot` — берётся, только если появится ряд, который первая не тянет. Заводить обе
  сразу — двойной словарь на один экран.
- Тепловая карта глубины — своим canvas, если понадобится: готовая библиотека под этот
  вид даёт больше ограничений, чем кода экономит.

### Прореживание ряда объявляется на экране

Ряд длиннее экрана приходится прореживать. Молчаливое прореживание превращает выброс —
единственную цену, ради которой график и открывали, — в несуществующее событие. Поэтому
шаг прореживания печатается на экране.

Альтернатива — агрегировать на сервере — отвергнута: это вернуло бы вычисление в
хранилище на пути фактов.

### Путь фронтенда — `web/`

В наборе правил три разных ответа: `project-naming-and-setup.md` §4 говорит
`src/frontend/`, правила TypeScript — `web/`, соседний репозиторий использует
`frontend/`. Берём `web/`: команды гейта в правилах фронтенда написаны литерально «из
`web/`» и при другом пути просто не выполнятся. Расхождение идёт в тот же issue наверх в
`nova/meta/rules`, что и расхождение про layered.

`bun.lock` живёт в `web/` — корень репозитория лок-файлов не держит
(`project-naming-and-setup.md` §1).

### i18n принимается как есть

Две локали для инструмента с одним оператором выглядят избыточно. Локального отклонения
всё равно не заводим: выдирать хардкод из готовых экранов задним числом дороже, чем
класть ключ на строку сразу.

## Risks / Trade-offs

- **Два процесса — две точки настройки пути к озеру** → расходятся молча и ломаются
  непонятно. Смягчение: разрешение пути одним правилом (`config-resolution.md`), API при
  старте печатает разрешённый путь.
- **DuckDB на запрос при частом опросе экрана** → задержка и расход. Смягчение: интервал
  в запросе обязателен, выдача ограничена; если замер покажет проблему — кэш вводится
  после замера, а не до.
- **Порождённый клиент ломает сборку фронтенда при правке контракта** → это и есть
  желаемое поведение, но оно делает гейт фронтенда зависимым от бэкенда. Смягчение:
  описание контракта коммитится в репозиторий, порождение — шаг сборки, а не запрос к
  живому серверу.
- **Графики — единственное нерегламентированное место** → выбор может оказаться неверным
  на реальных объёмах. Смягчение: `uplot` назван запасным заранее, решение принимается
  замером на реальном ряду, а не спором.
- **Фронтенд конкурирует за время с моделями и сигналами** → риск назван в самом
  proposal и снимается очерёдностью: изменение не стартует до появления первых сигналов.
- **Гейт фронтенда агент прогоняет не полностью** → `dev`, `vite`, `--watch` и
  браузерные драйверы из-под агента не запускаются (`process/agent-runtime-safety.md`);
  визуальная проверка остаётся за оператором.

## Migration Plan

Миграции нет: изменение только добавляет. Откат — удаление `src/presentation/EveTrader.Api`
и каталога `web/`; озеро, домен и application не затрагиваются.

Порядок реализации задан зависимостями: контракт поверхности → порождение клиента →
экраны. Экраны состояния идут раньше рыночных: у них есть содержание уже сегодня, и они
проверяют всю цепочку от озера до браузера на данных, которые точно есть.

## Open Questions

- **Нужен ли отдельный ресурс истории по паре или хватает общего пути фактов?** Ответ
  зависит от того, какой объём отдаёт общий путь на реальном интервале. Замеряется при
  реализации, спеки и разбиение задач не меняет.
- **Шаг прореживания — на сервере или на клиенте?** Требование обязывает объявить шаг;
  где его считать, решается по замеру задержки. На контракт не влияет: в обоих случаях
  шаг едет в ответе.
